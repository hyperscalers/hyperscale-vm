# Execution semantics: deterministic parallelism, the clock, aborts, and fees

## 1. Conflict groups and canonical order

With verified effect sets, parallelism needs no speculation. The kernel's batch executor (`crates/kernel`) sorts a committed batch into canonical transaction-hash order, judges reservations, partitions the batch into conflict groups by the mode compatibility relation ([01-effects-and-routing.md](01-effects-and-routing.md) §2), executes groups in parallel, and applies effects in canonical order. The schedule is a pure function of committed content — every replica derives the same groups — so this is not optimistic concurrency and requires no reconciliation.

- Commutative modes widen the groups: a thousand deposits to one vault are one parallel group with a canonical delta fold, not a serial chain.
- A conflict group is a sequential chain against one overlay, so members see each other's writes: a group is the mechanism that makes committing a conflicting set safe rather than a hazard. Fifty withdrawals against a well-funded vault all succeed; only genuine overdrafts abort, at the floor.
- The dispatch seam is the host's thread pool; determinism lives in the schedule derivation, not the thread timing. Receipts are byte-identical across serial, parallel, and adversarially permuted worker schedules (INV-VM-RUN-1), and the harness pins that continuously as a metamorphic test.

## 2. No execution-position observability

The schedule's soundness rests on one closure property: the only order-sensitive channels are declared effects, which the compatibility relation forces into conflicts that canonical order then resolves identically everywhere. The environment therefore never leaks schedule position — no intra-block index, no "transactions before me," no per-execution entropy at all — a draw is a function of a commitment the package made earlier. Every environment addition is checked against this rule first. ID generation already respects it: fresh object IDs hash the signed envelope and the call site's position, with no allocation counter, so uniqueness needs no coordination and no sequencing.

## 3. The transaction clock and the sealed draw

Replicated execution forces a single clock value per transaction: every participant computes the same receipt, so a component can never read "its own shard's" time. The clock is **the canonical weighted-time anchor of the payer-shard block that committed the transaction** — available at exactly the right moment on both sides: locally the anchor exists at the instant of commit, and remotely it rides the commit proof every non-payer participant already requires before engaging ([08-host-integration.md](08-host-integration.md) §2). Single-shard transactions degenerate cleanly, and application-visible time is coherent with the finalization deadline, which anchors on the same instant.

The monotonicity contract is explicit: exact along one payer chain, approximate globally — successive transactions at one component may carry clocks from different payer chains, with regression bounded by the Byzantine skew envelope plus commit lag. Stdlib time arithmetic saturates ([07-stdlib-and-upgrades.md](07-stdlib-and-upgrades.md)), so applications never see negative elapsed time.

Randomness is not the same shape, and the difference is the point. A clock a transaction carries is a fact about that transaction; a *draw* a transaction carries is a value the proposer of its committing block chooses. A shard reveal is a deterministic VRF over `(shard, height)`, so a validator holds every reveal it will ever produce; the block's chain folds its own, and the transaction hash is the only other input. That leaves a proposer free to grind hashes against a reveal it already holds and include the variant it likes. There is no execution-side fix for that, because the value exists before the ordering does.

A draw is therefore **sealed rather than carried**. A package seals a cell of its own; the kernel stamps the epoch the transaction is running in, and the draw that seal opens onto is `H(domain ‖ the beacon's seed for that epoch plus the protocol's maturity ‖ the cell's own key)`. Every input is committed state or a value the beacon rolled after the sealing committed. Nothing about the attempt that reads it enters — not its hash, not its sender, not the block that carries it — so two attempts at one seal answer alike, and abandoning one, running it out of fuel, or resubmitting it gains nothing.

The epoch is the kernel's and not a parameter, which is what makes the seal a commitment rather than a claim about one. A body that named its own would name an epoch already rolled — public seed, public word — and open onto a value it had computed before deciding to seal at all. So the seal cell holds what the kernel put there and nothing else: no package writes one, reads one back, or reaches its content.

The seed is the beacon's own, the same value that samples committees: a network whose randomness is not good enough to pick a winner is a network whose randomness is not good enough to pick the committee securing the shard. What an adversary can still do to it is the window edge priced in the committee-security analysis — holding a cut slot lifts their odds by a constant factor, about 1.23× at the design point.

That factor is what a package should be read against, and the bound it implies is **per ticket rather than per pot**: the multiplier does not depend on how many entrants a round has, so a bigger pot arrives with a proportionally smaller win probability and the two cancel. A round is worth biasing once a *single entrant's stake* exceeds roughly four missed proposals. A pot may be arbitrarily large below that.

Maturity is two epochs, so no part of the seed exists when the seal is written. A settlement before then declines and settles later; one past the retained window declines for good and the round closes again. Both are the package's own refusals rather than traps.

Nothing reads the current epoch's seed, and nothing reads the current epoch. A seed is public the moment it rolls, and so is every word derived from it, so a body that could read one would be reading a value anyone could grind their own inputs against for the length of an epoch — and a body that could read the epoch would be reading the one input the seal exists to keep out of its hands.

## 4. Abort taxonomy

Aborts are load-bearing in a deterministic cross-shard protocol — deadline all-aborts, race tiebreaks, reshape fences — and static access deliberately adds a retry class (stale declarations). Induced aborts must therefore never be free.

**Every class pays the same price: the declaration's.** What a transaction declares is what it is charged, on every outcome — a completion, a trap, a lost race, a deadline nobody caused. The network routed, provisioned and ran a batch for it whichever way it ended, and a schedule that discounted any ending is one an adversary picks the cheap entry from. There is no class floor and no surcharge, so the classes below name what happened and never what it costs:

| Class | Meaning |
|---|---|
| **User error** | Gate trap (undeclared access), auth failure, guest panic, fuel exhaustion |
| **Infeasibility** | Lost a deterministic race: reservation infeasible, debit or settle past the floor an earlier transaction in the group left, a credit past the width the cell has left, a write's presence requirement the committed leaf no longer meets, stale declaration |
| **Protocol** | Finalization deadline, reshape fence, recovery fence — no counterparty at fault |

The class is still recorded per receipt in the committed outcome, because it is what a sender needs to know whether to retry and what an operator needs to read a shard's health by; the host's certificate carries a coarser verdict. Griefing accounting falls out of the one price: a transaction engineered to abort held locks and burned remote work, and it pays the full declaration for the privilege, so the attack is paid and linear.

Where a class is ambiguous between defect and race, it is priced as the race. A credit past a cell's width is one such: what the width could not hold is the state's condition — an issuer filled the cell to within a credit of the maximum — and not the body's, so it lands in this row whether the exclusive hold refuses it at the call or the fold refuses it at commit; the two are one condition and carry one price. A sender who declared `create` on a leaf that already existed and one whom somebody beat to it leave identical state, so the protocol cannot separate them; charging the ceiling would bill every honest loser to reach the careless caller, and would turn any leaf a third party can create into a lever for spending somebody else's declared maximum. The same reading puts a presented authority a target no longer admits in this row rather than the one above.

**A decline is not an abort.** A method may carry a refusal channel and return through it — the guest ran to completion and said no on its own terms, which is a different event from any row above and is priced as one: the transaction does not commit, but the invocation is charged the fuel it actually spent rather than the ceiling a trap is charged, because an export that returned reaches an ordinary completed figure both engines derive by construction. What comes back is an index into the package's own table of refusals, so a receipt records which refusal rather than a string an author chose. Whether a method has the channel at all is a fact about its compiled type that the publish gate holds it to ([01-effects-and-routing.md](01-effects-and-routing.md) §9) — a vault deposit, which the kernel performs and which cannot decline or trap, is what lets a caller commit against it without waiting.

## 5. The fee quantities

**Five dimensions, one table, one price.** A transaction declares a vector, each dimension in its own unit, and the fee is the table-weighted sum. They stay a vector until the fee because the resources are not one resource: a block of scan-heavy transactions saturates disk while compute idles, and no scalar can see it — so each dimension is capped on a block's own content, and the table that weighs them into a fee is one consensus value the host moves once per epoch ([08-host-integration.md](08-host-integration.md) §2).

Every figure is a pure function of signed content and published metadata. Nothing measured enters it: what an execution consumed is reported in its receipt and prices nothing, because a figure an engine measured about itself is one a shard could inflate to raise its own emission weight. And because the vector derives from the declaration alone, every participant of a cross-shard transaction reaches one price before anything runs — which is what lets a shard that ran one leg bill the same as one that ran the whole.

1. **Compute** — the per-node fuel ceilings the composer signed ([01-effects-and-routing.md](01-effects-and-routing.md) §8), plus the verification of every signature the envelope binds. Verification is admission's compute: it is paid before an execution exists and it enters the same dimension, in the same unit. There is no refund on the slack. A refund is a promise about a measurement, and the measurement is the one thing a fee here never reads; what disciplines over-declaration is that the ceiling is priced whole and a preview fills it from a real run ([08-preview](../crates/preview)).
2. **Read bytes** — what the declaration reads off the store: `(cap + 1) × width` per declared range, the slot's width per declared point, and each distinct package's artifact once, since instantiating a node reads it. The range term is the prepay: a scan's page is paid for before it is walked, so what bounds a scan is the fee rather than a debt settled after.
3. **Write bytes** — what it writes onto the store, on the same terms, plus the cells the kernel writes of its own accord at their fixed widths.
4. **Declaration footprint** — declared keys and modes, priced per shard touched, per exclusivity class, and — for range targets — per order-of-magnitude of the declared interval. Looseness and hot exclusive access are metered, which pushes toward tight declarations, commutative modes, and argument lifting without any protocol mandate. Two shape facts are load-bearing. First, **the exclusivity ordering is the lattice's, and `read` is not where intuition puts it**: counted off the compatibility relation, `write` excludes four kinds, `read` three, `delta` and `reserve` two each, `locked` none. A fresh read is *more* disruptive than a delta — two deltas on one amount cell coexist, and a single fresh read on that cell conflicts with both — so pricing reads below reservations would make the cheapest declaration on a hot cell the one that serializes the most traffic across it. The weights derive from the relation rather than being tabulated beside it, so the two cannot drift. Second, **range width prices exclusion and the range cap prices depth, and the terms add rather than multiply**: an interval spanning a whole collection excludes every other declaration on it, so width is charged in orders of magnitude claimed — what occupies an interval is state a signing-time price may not read — while the cap is charged as the walk it buys, a per-scan seek floor plus the entries the cap admits. Exclusion is a property of the interval whatever it holds and depth a property of what the body walks; a claim can be wide and shallow or narrow and deep, and multiplying would price those as one claim twice over. The seek floor derives from the same constant the fuel schedule's per-scan floor derives from, so the two schedules state one figure. The computed quantity lives in `crates/effects` as the footprint; the unit prices are economics calibration.
5. **Retention bytes** — the envelope, the writes, the auth material, and the events a manifest's calls may emit between them: bytes every validator keeps and gossips for the horizon. The event term is the called method's own declared bound rather than a figure the sender picks, so a method that emits nothing may emit nothing and a node's slack is never another's to spend. Unpriced receipt bytes would be a cheap amplification attack on exactly the retention budget the chain is sized around.

Two quantities named here in earlier designs are not dimensions. **Lock occupancy** is not: hold time is not a signed figure, and what exclusion costs is already what footprint prices. **The storage bond** is not either — it is a deposit rather than a fee, returned when the state it covers is deleted, and it wants a design of its own ([03-objects-and-state.md](03-objects-and-state.md) §3) rather than a sixth row here.

## 6. Where a ceiling comes from

Block budgeting runs on the declaration because determinism gives replay exactness, never proposal-time exactness: static access fixes which keys are touched, not value-dependent control flow, and a cross-shard transaction cannot be pre-executed at proposal — its provisions do not exist yet.

The ceiling is **per manifest node**, signed by the composer in walk order, and each node is metered against its own figure. One figure for the whole would let a node that overran spend a neighbour's slack, which makes the composition's arithmetic rather than the method's behaviour decide who traps; per node, an exhaustion names the call that caused it. A node the envelope leaves unbounded is a composition defect and is priced to nobody.

Where the figure comes from is a preview: the transaction is run whole against the state it declares, and the per-node fuel it spent comes back with a margin over it ([the preview library](../crates/preview)). That is a measurement of one run against one snapshot, which is why the margin exists — value-dependent control flow can take a longer path over a balance that moved. Where cost is *decidable* the margin is unnecessary: a method whose control flow is independent of **state values** could carry a deploy-verified static bound in its metadata, and for that class the ceiling would be the computed figure with no slack at all. Environment inputs — the transaction clock, a matured seal's draw — are exact-class inputs, so vesting-style time arithmetic belongs in that tier. Nothing carries such a bound yet; the preview's margin covers every class meanwhile.

## 7. MEV posture

Static declarations make intent legible in the mempool — a visible effect set is a sandwich invitation. The posture is locked, not a shipped mechanism: the **effect set stays plaintext** (scheduling, routing, and locking need it), and the design must **not foreclose** threshold-encrypting the payload — amounts, bounds — until ordering commits. The transaction format keeps the manifest and the effect set separable, and nothing in admission requires payload plaintext before the block seals.

**Priority buys a place and never a position.** A sender may sign a priority as a multiplier on the price, burned with the rest of the fee, and what it buys is selection: a proposer filling a block takes the higher multipliers first. What it does not buy is where in the block the transaction lands — the order inside a block is hash order, checked by every voter, so nothing a sender pays moves a transaction ahead of one it shares a cell with. That is the half that matters for extraction: paying to be *included* sooner is a congestion price, while paying to be *ordered* ahead of a specific transaction is the sandwich, and the second is not on offer at any price.
